# 上下文管理：在 AI 变笨之前把活干完

> **核心前提**：AI 对话长度有限，上下文会退化。**这是结构性的，换个更强的模型也一样。**
> 所以正确的做法不是"避免退化"，而是**在退化之前完成可靠的工作**。

---

## 一、对话管理

### 1.1 一次对话聚焦一件事

一个对话 = 一个明确的、**可完成**的任务。

**反例**：「帮我开发这个功能」
**正例**：「修复列表页 6 个字段的数据绑定」

判断标准：**你能不能在开始时就说出"什么情况下这个对话算结束了"？** 说不出来，就是目标太大。

### 1.2 上下文预算意识

每次让 AI 读一个文件、理解一段逻辑，都在消耗预算。

**经验值**：对话开始时，**~70% 的预算应该留给实际工作**。如果准备工作（读规范、读代码、读背景）就消耗了 50%，剩下 20% 做实际的事——质量必然打折。

**任务卡模式的核心洞察**（见 [03-文件契约.md](03-文件契约.md)）：把准备工作从「读 8 个文件 1800 行」压缩到「读一张卡 80 行」。**省下的预算全部给实现。**

### 1.3 退化信号

出现 **≥2 条**就该考虑交接：

| 信号 | 表现 |
|---|---|
| 忘记约束 | 凭印象写代码，不再引用之前明确说过的规则 |
| 风格不一致 | 同一个文件里混用不同写法 |
| 重复劳动 | 做已经做过的事，或反复问已答过的问题 |
| 范围蔓延 | 开始改不该改的文件 |
| 输出变笼统 | 从"改了 auth.py:45 这一行"变成"优化了相关逻辑" |
| 反复横跳 | 改 A 破坏 B，改回来又破坏 C |

**应对**：**不硬撑**。输出交接文件，换新对话继续。

## 二、任务卡设计

（文件形态见 [03-文件契约.md](03-文件契约.md)，这里是设计要点）

### 2.1 自包含

任务卡应该是**读完就能干活**的独立文档。实现者不需要打开其他文件查信息。

**检验方法**：把任务卡单独给一个没参与过讨论的人（或新对话），问"你现在能开工吗？" 不能就是没写够。

### 2.2 约束要精确到文件名

```
❌ 不要碰其他地方
❌ 不要碰详情页
✅ 不要碰 user_detail_screen.dart
```

**为什么**：**AI 在上下文压力下，对模糊指令的解释会漂移。** 越模糊的约束，漂移空间越大。

### 2.3 目标措辞必须可验证

任务卡的"目标"和"约束"必须是**可事后实测**的断言。

```
❌ 重训要快
✅ 重训耗时 ≤ 30s（验收时计时）
```

无法事前验证的模糊约束（如"要流畅"）会变成事后扯皮。

### 2.4 内置角色提醒

任务卡末尾放一段角色边界提醒。**作用是在实现者翻到卡底时，再提醒一次它不能做什么。**

## 三、交接

**交接不是应急手段，是常规操作。** 这是本节最重要的观念。

### 3.1 三种交接

| 类型 | 触发 | 做法 |
|---|---|---|
| **正常交接** | 版本完成 | 输出交接文档 → 新对话读文件接住 |
| **压力交接** | 上下文退化 | AI 主动输出**可直接粘贴**的交接块 |
| **灾难恢复** | 对话丢了 | 新 AI 从磁盘文件重建状态 |

### 3.2 压力交接的关键：「粘贴即可用」

交接块本身就是**要粘贴的内容**——你复制，粘贴到新对话，零编辑。

**做不到"零编辑"的交接是不合格的**：如果每次交接你都要手动整理半小时，你很快就会放弃交接，然后硬撑着把活干砸。

### 3.3 里程碑交接

**长任务不必硬撑到一个对话耗尽。**

在**里程碑边界主动换新对话**——比如设计做完、实现做了一半、验收开始前。这是**计划内的续接策略**，不是应急手段。

**为什么**：在里程碑处交接，状态天然清晰（一件事刚做完）；撑到上下文炸了再交接，状态是混乱的（做到一半，到处都是未完成的改动）。

## 四、Checkpoint 模式

适用于复杂功能（≥3 个耦合的子模块/子界面）。

**把大任务切成若干检查点，每个检查点之间重新评估方向。**

以界面开发为例：

| Checkpoint | 产出 | 人确认什么 |
|---|---|---|
| 0 | 屏幕地图 | 层级和数据内容对不对 |
| 1 | 导航 + 结构 | 路由、Tab、骨架对不对 |
| 2 | 数据展示 | 字段、数据源、格式对不对 |
| 3 | 交互 + 验收 | 键盘、鼠标、快捷键、验收 |

**核心价值**：**错了在下一个检查点纠正，不等到最后才发现。**

一次性做完 10 个界面再验收，如果方向错了，10 个界面全废。分 4 个检查点，最坏情况废 2-3 个。

## 五、文档写作原则

> 适用于所有技术文档（教程、手册、spec）。目标：**零基础读者能顺下来，且每句话都有证据。**

### 5.1 读者默认零基础

每个关键章节开头，先用一句"用人话讲"打底（类比 + 大白话），再进技术细节。

### 5.2 英文名词带中文

英文名词**首次出现**必须带中文全称 + 一句话解释：

> `DFT（密度泛函理论，Density Functional Theory）——量子力学算单个分子电子结构的方法`

名词密集的文档，开头放一张**名词速查表**。

### 5.3 证据先于断言

声称"已验证 / 已通过 / 一致 / 可恢复"之前，**先跑验证命令拿到证据**，再把证据写进文档（校验和、diff 输出、检查结果）。

**没验证过的不写"已验证"**。二手来源的信息标注"未读原文"。

### 5.4 凡「约 N」，必附命令 ⭐

> **历史教训**：一次汇报里说「约 12 处违规」，是**抽样目测**。实际 80 处——**差 6 倍**，还漏报了两类实现。

**交付报告里凡出现数量**（「约 N 处」「大概 M 个」「覆盖 K 个文件」），**必须附上产出该数字的命令**——注意先分清口径，**数「处」和数「行」不是一回事**：

```bash
# 数「处数」——一行里出现两次要算两处
grep -o "pattern" file | wc -l
rg --count-matches "pattern"

# 数「行数」——grep -c 数的是匹配行，一行里两处只算一处
grep -c "pattern" file

# 数「覆盖了几个文件」
rg -l "pattern" | wc -l
```

**铁律**：没有命令的数字 = 不可信。**目测的数字下一个读到的人无法复算**，也无法判断是高估还是低估。

### 5.5 基线是「最后一步」，不是「第一步」 ⭐

> **历史教训**：某人取完工作树快照基线后，又继续写自己的记录文件，导致基线**不可复算**——验收的人拿到的是"已经变了"的基线，白耗排查成本。

**取任何基线/快照**（工作树状态、测试数、覆盖率、文件清单）时，必须在你**所有写操作完成之后**取。

**根因**是「收尾动作」和「取基线」的顺序颠倒：**先取基线，再写记录，基线就过期了。**

## 六、@context：代码里的文档引用

### 问题

AI 读代码时，**不知道有相关文档存在**。

### 方案

在关键源文件里嵌一行文档引用，AI 读代码时自然发现：

```python
# @context: docs/domain/01_核心概念.md — 领域术语的定义与约束
```

```dart
// @context: docs/platform-notes.md — 某些运行环境下的兼容性要求
```

**位置**：文件顶部，或关键函数/类上方。

### 原则

- **只在"理解这段代码需要外部知识"的文件里加** —— 不要批量添加
- **一行，不赘述** —— 文档本身有完整信息
- **零启动开销** —— AI 读代码时才看到，不占初始化预算

## 七、UI 打磨的一个补充模式

> 仅适用于涉及前端界面的版本。

**打磨时最大的风险是范围蔓延**——"既然改这个按钮，顺便把整个页面的样式也调一遍吧"。

用一个明确的边界表拦住：

| 类型 | 示例 | 处理 |
|---|---|---|
| 🟢 视觉 | 颜色、间距、字号、动画 | 打磨对话内直接改 |
| 🟡 交互 | 弹框、hover、事件流 | 改 + 补测试 |
| 🔴 功能 | 新增按钮、改业务逻辑 | **拦截** —— 不在本次范围内 |

**🔴 类必须拦截**：它看起来像"顺手的事"，实际上是范围蔓延的入口。

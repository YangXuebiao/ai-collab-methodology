# 实战切片：一个版本的完整生命周期

> 前六章讲的是原则。这一章把它们串起来——**跟着一个真实的版本走一遍**。
>
> 例子是虚构的，但流程和文件形态都来自实际使用。

---

## 场景设定

**项目**：一个内部的用户管理后台（Web 应用）
**版本**：V1.3.0
**需求**：运营同事说"我想把用户列表导出成 Excel，现在只能一页页复制，太慢了"

**参与的角色**：设计者（你，和 AI 对话 A）、实现者（对话 B）、验收者（对话 C）

---

## 第一阶段：设计

### 你这样说

```
你是这个版本的设计者。需求：用户列表页支持批量导出。

先不要动手，先写一份设计文档。重点说清楚：
1. 导出什么字段
2. 大数据量怎么办（我们有 20 万用户）
3. 怎么算做完了（可验证的验收标准）
```

### 设计者的产出（节选）

```markdown
# V1.3.0 用户批量导出 — 设计 Spec

## 一、背景与目标
运营需要导出用户列表做线下分析。当前只能逐页复制，
20 万用户按每页 50 条算需要翻 4000 页。

目标：列表页提供「导出」按钮，导出当前筛选条件下的**全部**用户。

## 四、核心设计

### 4.1 导出范围
导出「当前筛选条件下的全部结果」，不是"当前页"。
（理由：逐页复制的痛点就在翻页。若只导当前页，痛点未解。）

### 4.2 数据量处理
20 万行 × 12 列 ≈ 40MB CSV。
- 同步导出：请求会超时（实测网关超时 30s）
- 异步导出：生成任务 → 完成后通知 → 下载

**待定** —— 见「待决策」一节。

## 七、文件清单
- 新增：`src/api/export.py`
- 新增：`src/services/export_service.py`
- 修改：`src/api/users.py`（加端点）
- 修改：前端列表页组件
- 新增测试：`tests/test_export.py`

## 八、验收标准
1. 点击导出按钮后，导出的是**当前筛选条件下的全部**用户（不只是当前页）
2. 导出的 CSV 包含字段：ID、用户名、邮箱、注册时间、最后登录时间
3. 20 万用户全量导出**不会导致请求超时**（具体方式待决策，见下）
4. 导出完成后用户能拿到文件
5. 无权限的用户不能导出（返回 403）

## 待决策（B 类）
见下方决策请求单。
```

### 设计者同时产出一份决策请求单

```markdown
# 决策请求单：导出方式

## 选项
A. **同步导出**（请求内完成）
   代价：请求最长 ~2 分钟，网关会超时；需要调大超时配置，影响其他端点

B. **异步导出**（后台任务 + 下载链接）
   代价：需要引入任务队列（当前项目没有）；用户要等一会儿才能下载；
        需要新增「导出记录」页面

## 不可比理由
两者都能满足需求，且客观依据分不出优劣：
- 技术上：A 更简单但现在不成立（网关超时）；B 需要新组件
- **关键分歧在"要不要为这个需求引入任务队列"** —— 这是对项目
  未来演进的判断（后面还会有别的异步需求吗？），不是技术判断
- 若只看这个需求：A 改超时配置即可（但影响面未知）
- 若看未来：B 一次性投入，后面复用

## 默认建议
B（异步）。理由：20 万用户量下，同步方案的超时配置调整有未知风险；
且"导出"类需求通常不止这一个。

**但如果项目短期不会有其他异步需求，A 的短期成本明显更低。**
```

### 你返回后

```
用 B（异步）。你说得对，后面还有数据同步的需求也要走异步。
```

**注意这里发生了什么**：AI 停下来了、绕开了（它继续把不依赖这个决策的部分——验收标准 1/2/4/5——写完了）、记了单子、报了。**唯一的阻塞点就是这一个决策，其余部分没有停摆。**

---

## 第二阶段：分派

设计者把 spec 拆成任务卡：

```markdown
## 后端导出 任务卡 — 实现异步导出 API

### 你只需要知道这些
用户列表要支持导出全部筛选结果（20 万量级）。
同步会超时，所以走异步：提交任务 → 轮询状态 → 下载文件。

### 要做什么
1. 新增 `src/services/export_service.py`：生成 CSV 的核心逻辑
2. 新增 `src/api/export.py`：
   - POST /api/export — 提交导出任务，返回 task_id
   - GET /api/export/{task_id} — 查询状态，完成时返回下载链接
3. 修改 `src/api/users.py`：复用已有的筛选查询逻辑（不要重写）
4. 权限：复用 `require_admin` 装饰器
5. 测试：`tests/test_export.py`
   - 导出内容与筛选条件一致
   - 无权限返回 403
   - 任务状态流转正确

### 关键约束
- 导出上限 50 万行，超过返回错误（防止打爆内存）
- CSV 用流式写入，不要一次性在内存拼完

### 不要碰
- `src/api/users.py` 的**查询逻辑**（只加端点，不改现有函数）
- `src/services/user_service.py`
- 任何数据库 schema

### 完成后
更新 `docs/dev-status-V1.3.0.md`，列出：完成了哪些项、
做了什么假设、有没有偏离 spec。**不要提交代码。**

### 角色边界提醒
你是实现者：写代码和测试，不改设计文档，不提交代码。
```

### 三个设计点

- **「你只需要知道这些」** 5 行讲完背景 —— 实现者不用读完整 spec
- **「不要碰」精确到文件**，而且区分了"改这个文件"和"改这个文件里的某部分"
- **「完成后」明确要求写假设** —— 这是后面验收的关键输入

---

## 第三阶段：实现

实现者做完，写 dev-status：

```markdown
# V1.3.0 实现状态

## 已完成
- [x] export_service.py：CSV 流式生成
- [x] export.py：两个端点
- [x] users.py：新增端点（复用现有查询）
- [x] 权限校验
- [x] 测试 3 个用例

## 未完成 / 阻塞
- [ ] 任务队列接入 —— 卡在：项目里没有现成的队列，
      我用了一个简单的数据库轮询方案先顶上，可能不是最终方案

## 我做的假设
1. **导出任务存在数据库表里，用轮询查状态**（spec 没指定怎么存）
   —— 假设这是可接受的，因为项目已有 Postgres，不想为这个引入 Redis
2. **CSV 编码用 UTF-8 with BOM**（Excel 打开中文不乱码）
   —— spec 没提编码，我按 Windows 用户为主假设的
3. **下载链接有效期 24 小时**（spec 没提）

## 偏离 spec 的地方
- 无（假设 1 属于 spec 未覆盖，不算偏离）

## 磁盘上的改动
- 新增 3 个文件，修改 1 个文件，未提交
```

**看「我做的假设」这一节**——三个假设，每一个都是 spec 没写清楚、实现者自己填的。**如果不写下来，这三个就是埋着的雷。**

---

## 第四阶段：验收

**关键**：开一个新对话做验收。只给它 spec + dev-status + 代码。

```markdown
# V1.3.0 验收报告

## 逐项验收（对照 spec 第八节）
| 验收标准 | 结果 | 证据 |
|---|:---:|---|
| 1. 导出全部筛选结果（非当前页） | ✅ | test_export.py::test_export_all_filtered 输出 ✓ |
| 2. 字段完整 | ✅ | 导出的 CSV 表头：ID,用户名,邮箱,注册时间,最后登录时间 |
| 3. 20 万用户不超时 | ⚠️ 部分 | 用 5 万行测通过（耗时 8s）；**20 万未实测**（见未验证） |
| 4. 完成后能拿到文件 | ✅ | 手动验证：轮询返回 ready 后下载成功 |
| 5. 无权限返回 403 | ✅ | test_export.py::test_export_forbidden 输出 ✓ |

## 发现的问题
| 级别 | 问题 | 位置 | 处理 |
|:---:|---|---|---|
| 🟢 | 函数缺返回类型标注 | export_service.py:23 | 已修 |
| 🟡 | 缺"超过 50 万行返回错误"的测试 | tests/test_export.py | 记录，未改 |
| 🟡 | 假设 2（BOM 编码）无测试覆盖 | tests/test_export.py | 记录，未改 |
| 🔴 | **假设 1 的任务存储方案未在设计文档中确认** | export_service.py:40 | 记录，未改 |

## 未验证的部分
- **20 万行全量导出未实测**（只测到 5 万）。需要造数据，本次时间不够。
- 下载链接过期行为未验证
- 并发多个导出任务未验证

## 真实数据验证
- 用了生产库的脱敏副本（5 万条），非合成数据
```

### 这份报告的价值在哪

- 🔴 **那条**：验收者发现"实现者自己选的存储方案没经过设计确认"——这是设计者应该知道的事。**验收者不认识实现者，所以它看到的是"spec 里没这个"，而不是"哦我当初是这么想的"。**
- **「未验证的部分」列了三条**。这份报告没有假装全覆盖。
- **每个 ✅ 都有证据**，不是"我检查过了"。

---

## 第五阶段：收尾

设计者看过 qa-report，处理 🔴，然后写完成报告：

```markdown
# V1.3.0 版本完成报告

## 一、交付摘要
用户列表支持异步导出全部筛选结果（CSV，上限 50 万行）。

## 四、已知问题
- 任务存储用的是「数据库表 + 轮询」，不是专业任务队列。
  **量再大需要迁移**（当前 20 万量级够用）
- 下载链接 24 小时有效期是**实现时定的**，未经产品确认
- 20 万行全量导出**未实测**

## 六、下一版本
- 20 万行实测（本次欠账）
- 导出记录页面（异步方案的下半部分，本次没做）
- 若引入任务队列，把当前轮询方案迁过去

## 七、反馈分类
- P | 🟡 | 设计文档没有"异步任务的存储方案"槽位，实现者只能自己填
       建议：spec 模板加一节「新增持久化」
```

**「已知问题」和「下一版本」这两节**，是给三个月后的你看的——那时候你已经忘了"下载链接 24 小时是当时随手定的"。

## 一条额外的经验：多会话并行

**如果你同时开多个 AI 对话改同一个仓库**（比如一个改后端一个改前端），有一条经验值得记住：

> **每次提交前，明确列出要提交的文件路径，不要让 AI 用 `git add -A` 或 `git add .`。**

**原因**：另一个对话可能正在修改别的文件、还没写完。全局 add 会**把别人没完成的工作一起卷进你的提交**。

实际发生过：一个对话提交时卷走了另一个对话正在改的 27 个文件，导致后者的工作状态被破坏，排查了很久。

**正确做法**：

```bash
git add path/to/file1.py path/to/file2.py   # 明确路径
git commit -m "..."
```

**判断标准**：你提交的每一个文件，你都能说出"它为什么属于这次改动"。说不出，就说明它是被卷进来的。

## 回到整体

这个版本走完，你得到了什么？

| 产物 | 价值 |
|---|---|
| spec | 三个月后回看，知道**当初为什么这么设计** |
| 任务卡 | 实现者不用读 2000 字背景，省下的预算给了代码质量 |
| dev-status 里的**假设** | 三个"猜"被记录下来了，不是埋着的雷 |
| qa-report 里的**未验证项** | 你知道这版**没测什么**，而不是以为全覆盖了 |
| completion-report | 下一版的起点 |

**如果省掉这些**：这个版本也能上线。但三个月后你改这块代码时，会面对一堆"当初为什么这样"的疑问，而且没人能回答。

**这就是这套方法论的成本与收益**：记录确实要多花时间——按我们的经验，一个有实质设计的版本大约多花半天到一天（**这是经验估计，没有精确统计**）；换来的是几个月后回头改这块代码时，不必靠考古去重建当时的取舍。

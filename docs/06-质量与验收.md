# 质量与验收

> 这一章回答一个问题：**怎么算做完了？**
>
> 包含四块：验收怎么做（§一–§三）、**评估怎么评（§四，最有价值）**、破坏性操作怎么防（§五）、**单人开发怎么用（§六）**。

---

## 一、验收为什么必须独立

**验收者不能是实现者。**这是整章的前提。

**原因不是"不信任"，是结构性的**：

- 人对自己的产出会有主观投入，倾向于挑对自己有利的解释
- 实现者脑子里全是"我为什么这么做"——它看不到"我这么做对不对"
- **AI 尤其如此**：它会顺着自己的实现逻辑去解释需求，然后确认自己是对的

**所以**：验收要在一个**干净的上下文**里做——只给它验收标准 + 最终结果，不给它实现过程的讨论。（单人开发的具体做法见 [02-角色分工.md](02-角色分工.md) §五）

## 二、问题分级

验收时发现的问题，按**客观标准**分三级——不靠"感觉严重不严重"。

### 小（🟢）— 验收者直接修

满足**全部**条件：

- 改动 ≤ 5 行
- 只涉及单个文件
- 不改函数签名、不改数据流逻辑

典型：类型标注遗漏、错误消息文本、注释补充、格式不一致、明显拼写错误。

### 中（🟡）— 记录，不改

满足**任一**条件：

- 需要新增文件或新增函数
- 缺少测试用例
- 缺少边界条件处理（需要加新逻辑分支）
- 改动涉及 ≥ 2 个文件

典型：少了一个测试、空值未处理、响应格式不完整。

### 大（🔴）— 记录，不改，**且阻塞**

满足**任一**条件：

- 需要改接口签名（函数参数、API 路径、数据模型字段）
- **结构性**违反项目的硬性规范（依赖方向被破坏、架构红线）
- 涉及安全问题或数据完整性问题
- **设计文档本身有缺陷**（需要重新设计）

> ⚠️ 注意区分：**数值型门槛的轻微超出**（覆盖率差几个百分点、文件超几十行）属 🟡，不阻塞——见下方速查表。判 🔴 的是**结构性**违反，不是数字差一点。

典型：API 路径与设计文档不一致、数据模型缺关键字段、性能退化。

### 边界案例速查

| 发现 | 级别 | 理由 |
|---|:---:|---|
| 少了一个类型标注 | 🟢 | 单文件、≤5 行、不改逻辑 |
| 错误消息写错了 | 🟢 | 单文件、改字符串 |
| 边界条件未处理（空列表） | 🟡 | 需要加新逻辑分支 |
| 少了一个测试用例 | 🟡 | 需要写新测试 |
| API 路径与设计文档不一致 | 🔴 | **可能是文档错了**——需要确认 |
| 数据模型缺字段 | 🔴 | 影响所有下游 |
| 覆盖率 79%（门槛 80%） | 🟡 | 不改代码但需记录 |
| 文件 210 行（上限 200） | 🟡 | 需要拆分，涉及新文件 |

### 不确定时的默认规则

> **向上取一级。**
> 不确定是 🟢 还是 🟡 → 按 🟡（记录不改）
> 不确定是 🟡 还是 🔴 → 按 🔴（记录不改，标记阻塞）

**为什么向上取**：漏报一个真问题是事故，误报一个假问题只是多记录一条。**代价不对称。**

## 三、验收报告的两个硬要求

### 1. 「证据」列必须非空

每条验收结论都要指向一个**具体输出**：测试结果、命令输出、日志片段。

```
❌ 我检查过了，没问题
❌ assert 429 == 429 恒为真，跑一万次也不会红——它证明不了接口返回了 429
✅ 连续 5 次错误密码后锁定 —— 见 test_lockout.py:45 输出：assert resp.status_code == 429 ✓
```

> 判据是**这条断言会不会变红**。恒真的断言不是证据——这与精神内核第 4 条「永远绿灯的检查比没有检查更糟」是同一条道理。

### 2. 「未验证的部分」不能空

**大多数时候是有遗漏的。写出来，比假装全覆盖强得多。**

```
## 未验证的部分
- 并发场景下的锁定行为未测（需要压测环境，本次没搭）
- 邮件通知的实际发送未验（用 mock 替代）
```

**这一节是验收报告可信度的来源**。一份"全部通过、无遗漏"的报告，读者会怀疑；一份明确列出遗漏的报告，读者会信任它说的"通过"。

## 四、评估规范：六条铁律 ⭐

> **如果你要做算法选型、模型迭代、性能优化、检索调优——这一节请完整读完。**
> 它来自一次真实事故，代价很大。

> 📖 **本节是主干速览。**完整操作版（可复制的报告模板、反例对照表、在你项目里怎么落地）在 [reference/评估规范.md](reference/评估规范.md)。
> **两者如有出入，以 reference 为准**——本节是索引，它是操作版。

### 4.1 事故经过

一次算法选型，AI 用**「10 个参数的平均误差」**对比三个方案，得出结论：

> 「方案 C 最优，优于其他 17~33%」

并且**多轮"验证"都维持这个结论**。

后来换用**尾部指标**（P90）重新评估，发现：

> **方案 C 在某个参数上，尾部误差比其他方案差 20~100 倍。**

它只在中位数上略好，**尾部灾难性地差**。结论被彻底推翻——方案 C 其实是最差选择。

### 4.2 根因：尺子错了，不是算错了

- 各参数**单位天差地别**（一个 ~1.6，一个 ~67），跨参数求平均**在数学上就没有意义**
- 这个平均恰好**掩盖**了单项的 20~100 倍回退
- 此后每一轮"验证"都用**同一把看不见问题的尺子**，自然每轮都得到同一个"好"结论

> **结论：多验证几轮纠不了这种错。换指标比多验证更重要。**

### 4.3 六条铁律

#### 铁律 1：先定"真正关心的指标"

用反映**业务/用户关切**的指标，不用"方便统计"的指标。

**判据**：报告须显式写出「本次评估的口径」，并说明它对应哪个关切维度（精度？极端情况？成本？风险？）。**写不出对应关系 = 未通过。**

#### 铁律 2：禁止用聚合指标下结论

**禁止**出现「整体改善 17%」这类**跨单位/跨对象求平均**的结论。

**判据**：报告须含**逐项对比表**（每个被评估对象一行）。只给聚合数 = 未通过。

#### 铁律 3：尾部指标并列

必须**同时**给出 `p50 / p90 / p99 / max`（或该领域的等价口径），**不得只给中位数或均值**。

**判据**：逐项对比表须含至少一个**尾部列**。缺 = 未通过。

> 为什么：**用户实际遇到的往往是尾部情况**，而中位数看不见尾部灾难。

#### 铁律 4：先做「旧 vs 新」逐项对比，标出**所有**回退

对比表须**同时含旧值与新值**，并**逐项标出**哪些变差了。

**判据**：列须含「旧值 / 新值 / 变化」三列；回退项须显式标记。缺 = 未通过。

#### 铁律 5：回退超阈值即停

**阈值必须在评估前声明**，不得看完结果再定。任一子集回退超阈值 → **停下来查，不得放行**。

**判据**：报告须含「阈值声明」节。**事后补的阈值 = 未通过。**

> 为什么强调"前置"：看到结果再定阈值，阈值就沦为**事后合理化**的工具——总能定一个刚好能通过的数。

#### 铁律 6：结论必须附「反例 / 还没查什么」

**禁止只列支持证据。**每下一个结论，须同时给出：有没有反例？哪个子集会变差？我还没查什么？

**判据**：报告须含「反例 / 未查项」节且**非空**。只有支持证据 = 未通过。

### 4.4 报告骨架

**可复制的骨架见 [reference/评估规范.md](reference/评估规范.md) §三。**

这里不再复述——这一段曾与它**逐字重复**，而且两边已经开始不一致。这正是「信息唯一性」要防的：**多处复述就是信息不唯一的信号**。

> ⚠️ 抄骨架时注意：逐项对比表必须含 **p99 列**。铁律 3 要求 `p50 / p90 / p99 / max` 四项并列，少一项就不合格。

### 4.5 反例对照表

| ❌ 错误做法 | 后果 |
|---|---|
| 跨单位求平均 | **无意义**，且掩盖单项 20~100 倍回退（**已致事故**） |
| 只报中位数 | 看不见尾部灾难；用户遇到的恰是尾部 |
| 只给新值，不给旧值 | 无法判断谁变差了 |
| 看到结果再定阈值 | 阈值沦为事后合理化 |
| 只列支持结论的数据 | 越验证越像凑支持，纠不了错 |
| 出问题先归因数据/环境/历史 | 漏掉"是不是我刚改的导致的" |

### 4.6 「用户直觉」与「成事不讨好」的边界

这两条看起来冲突，实际不冲突：

> **用户的直觉当「触发信号」（换个指标重测），不当「结论」（直接照做）。**

- ✅ 用户说"太绝对了" → **立刻换指标（尤其尾部）重测** → 用数据说话
- ✅ 重测后数据支持原结论 → 如实说"换指标重测后仍成立"，给出证据
- ❌ 用户说"太绝对了" → 不测就改口（**这是讨好**）
- ❌ 用户说"太绝对了" → 不测就继续辩解、堆更多同口径的数据（**这是这条规范要治的病**）

**注意**：那次事故里，正是用户"凭直觉觉得太绝对了、像在凑数据"的质疑，才发现了问题。**直觉是宝贵信号，只是它需要被转化成验证动作。**

## 五、破坏性操作的安全原则

> 从生产事故中泛化出来的经验。核心是**"默认安全，可覆盖"**。

### 5.1 执行前显式声明目标

任何涉及**删除、重建、清空**等不可逆操作时，**显式声明目标环境**，禁止用"当下系统"、"当前环境"这类模糊说法。

| ❌ 模糊 | ✅ 显式 |
|---|---|
| "清除当下系统下的容器" | "清除**你的本地机器**上的 X 容器" |
| "部署到服务器" | "部署到 **192.0.2.10 生产服务器**" |
| "重启服务" | "重启 **生产机**上的 X 服务" |

**为什么**：这些操作一旦执行错环境，代价不可逆。模糊指代是事故的温床。

### 5.2 三段式确认

在**远程/生产环境**执行破坏性命令前，发一段独立的确认提示：

```
⚠️  即将在 <目标环境> 上执行以下操作：
  - docker compose down -v （停止并删除所有容器和 named volume）
  - 受影响资源：3 容器 / 2 网络 / 1 named volume / 0 镜像
  - 不可自动撤销

确认？[输入 yes 继续 / 输入其他取消]
```

**三个要素**：目标环境 / 具体操作和影响面 / 不可撤销声明。

### 5.3 默认安全，可覆盖

项目脚手架提供的安全配置（备份、权限、隔离）是**起点**。要覆盖时必须：

1. 理解默认配置**保护了什么**
2. **记录覆盖原因**
3. 确认替代方案提供了**同等或更强**的保护

## 六、单人开发怎么保证验收质量

三个可操作的降级方案（效果递减）：

| 方案 | 做法 | 效果 |
|---|---|---|
| **换对话验收**（最佳） | 新开一个对话，只给它设计文档 + 验收标准 + 最终代码 | 上下文干净 |
| **同对话显式切换** | 明确声明"现在以验收者身份，只对照标准核对" | 上下文有残留 |
| **清单化自查** | 把验收标准逐条列出来，逐条找证据 | 最弱，但比"感觉没问题"强 |

**底线**：**至少要做第三条**。把"我觉得应该没问题"换成"这 5 条验收标准，我逐条找了证据"——这一步的性价比极高。

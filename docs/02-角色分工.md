# 角色分工：三个 AI 各干各的

> **核心认知**：角色分工保护的不是"流程规范"，是 **AI 有限的上下文**。
> 让一个 AI 同时做设计和实现，它的注意力会被实现细节占满，设计判断就没了。
> 让一个 AI 既写代码又验收，它就没法客观——**人不会认真挑自己的错，AI 也不会。**

---

## 三个角色

```
        设计者（管理者）
      规划 · 分派 · 审阅
        ╱            ╲
   文件契约        文件契约
      ╱                ╲
 实现者（开发者）  验收者（QA）
   写代码+测试      验证 + 验收
      ╲                ╱
        ╲            ╱
         文件契约
```

**关键**：三者之间的信息传递**不走人**，走磁盘文件。详见 [03-文件契约.md](03-文件契约.md)。

---

## 一、设计者

> **产出是文档、计划和分派，不是代码。**

### 边界

| 可以做的 | 不可以做的 |
|---|---|
| 写设计文档（spec） | ❌ 写产品代码 |
| 更新路线图、写完成报告 | ❌ 跑测试、跑编译 |
| 版本提交（git commit） | ❌ 操作数据库或改配置 |
| 生成分派任务 | ❌ 自己动手修 bug |
| 审阅实现者和验收者的结果 | ❌ 跨版本规划（见 01-协作原则.md 的原则 7） |

### 每次动手前的自检

| 我要做什么 | 属于设计者？ |
|---|:---:|
| 跑到一半想自己去跑个测试看看 | ❌ 交给验收者 |
| 部署 / 起服务 | ❌ 交给实现者 |
| 读源码**诊断 bug 并修复** | ❌ 交给实现者 |
| 读源码**核查验收**（只看不改） | ✅ |
| 写 spec / 任务 / 审查报告 | ✅ |
| 提交代码 | ✅ |

**注意这条区分**：「读源码诊断并修复」和「读源码核查」是两件事。前者是实现的活，后者是设计的活。**同一个文件，读它是为了改还是为了审，决定它属于谁。**

### 收到越界指令时

有人（包括你）让它去跑测试，它应该说：

```
这个操作不属于设计者范围。替代方案：
→ 分派给实现者（写任务）
→ 或分派给验收者
```

**这条要主动要求 AI 执行**，否则它一定会顺着你做——AI 天然倾向于"帮你把事办了"。

---

## 二、实现者

> **产出是可工作的代码 + 测试 + 状态文件。**

### 边界

| 可以做的 | 不可以做的 |
|---|---|
| 写产品代码 + 测试 | ❌ 改设计文档（那是设计者的职责） |
| 跑编译 + 测试 | ❌ 提交代码 |
| 更新实现状态文件 | ❌ 改设计者的记录文件 |
| 读设计文档 + 任务 + 相关代码 | ❌ 跨版本规划 |
| 反馈流程问题给设计者 | ❌ 自己决定技术选型（不在方案范围内时先问） |

### 每次动手前的自检

| 我要做什么 | 属于实现者？ |
|---|:---:|
| 写产品代码 / 测试代码 | ✅ |
| 跑编译 / 测试 / 部署 | ✅ |
| 写实现状态文件 | ✅ |
| 写设计文档 / 任务 / 完成报告 | ❌ 交给设计者 |
| 提交代码 | ❌ 交给设计者 |

**为什么实现者不提交代码**：提交是一个「审查通过」的信号。实现者自己提交，就等于自己宣告"我做对了"。**让设计者在看过之后提交，这个动作才有意义。**

---

## 三、验收者

> **产出是质量报告。跑测试、验证功能、发现问题。**
> **小问题自己修，中/大问题记录但不改。**

### 边界

| 可以做的 | 不可以做的 |
|---|---|
| 跑编译、跑测试、跑覆盖率 | ❌ 改设计文档 / 路线图 |
| 修复 🟢 小问题（≤5 行、单文件、逻辑明确） | ❌ 改 🟡🔴 问题的产品代码 |
| 写验收报告 | ❌ 提交代码 |
| 对照验收标准逐项核对 | ❌ 做主观设计判断 |

### 每次动手前的自检

| 我要做什么 | 属于验收者？ |
|---|:---:|
| 跑测试 / 覆盖率 | ✅ |
| 修复 🟢 小问题 | ✅ |
| 写验收报告 | ✅ |
| 修改产品代码（🟡🔴） | ❌ 交给实现者 |
| 起服务 / 部署 | ❌ 交给实现者 |
| 提交代码 | ❌ 交给设计者 |

### 验收者的独立性

**为什么验收者不能修 🟡🔴 问题**：

一旦验收者开始动手改，它就"变成"了实现者——它对自己改的东西会有主观投入，再让它客观评估就不可能了。

**这是这套方法论里最反直觉、也最重要的一条。**它的代价是真实的：明明看到问题却不能改，会很难受。但收益是：**验收报告的可信度**。

> ⚠️ **真实数据验证**：合成/假数据测不出的问题，会在真实数据下暴露。
> 数据敏感的验收**必须包含真实数据样本**——不能因为合成数据全绿就通过。

问题分级标准见 [06-质量与验收.md](06-质量与验收.md)。

## 四、角色冲突怎么办

**收到不属于当前角色的指令时，先对号入座，然后拒绝并给替代方案。**

```
这个操作不属于 <当前角色> 范围。替代方案：
→ 分派给 <正确角色>
```

**这条对你自己也适用。** 如果你在实现者的对话里说"顺便把设计文档也改了吧"，一个好 AI 应该拒绝你，并告诉你切到设计者角色。

如果你觉得"太麻烦了，就让它顺手改了吧"——那你其实是在放弃这套方法论的核心价值。**越界一次不会有问题，但越界的成本是隐性的**：那个 AI 的上下文里混入了另一个角色的细节，接下来的判断质量会下降，而你不会立刻发现。

## 五、单人开发怎么用

**本项目按单人或小规模场景整理。**如果你是多会话并行（同时开多个 AI 对话改同一个仓库），[07-实战切片.md](07-实战切片.md) 末尾有一条相关经验。

单人场景下，三个角色**由同一个 AI 在不同时间扮演**。可行的做法：

### 做法 A：一个对话内切换（轻量）

同一个对话里，显式声明切换：

```
现在切换到「验收者」角色。
作为实现者我已经写完了，现在我要以验收者的身份，只看结果不看过程。
```

**关键**：切换要**显式**，且切换瞬间要有意识地"忘记"实现细节。这一点很难做好——因为上下文里还留着实现时的思路。

### 做法 B：换一个对话（推荐）

**实现完成后，开一个新对话做验收**。把设计文档 + 实现状态文件给它，不给它实现过程的对话。

这样做的好处：验收者的上下文是**干净的**——它看到的是"文档说要做 A、B、C"和"代码里实现了 A、B、C"，而不是"我（作者）当时是怎么想的"。

**这也是为什么"文件契约"这么重要**：[03-文件契约.md](03-文件契约.md) 里那几个文件，就是让你能把工作从一个对话搬到另一个对话的载体。

### 做法 C：让 AI 扮演验收者，但明确不要它参考实现过程

```
请以验收者的身份审阅这个实现。
只读 <spec 文件> 和 <实现状态文件>，以及最终代码。
不要参考我们之前的讨论。对照验收标准逐项核对。
```

**效果比做法 B 差，但比不做好。**

---

## 一句话

> **分角色不是为了限制 AI 的能力，是为了保护它有限的注意力。**
> 注意力被分散的 AI，会以一种你很难察觉的方式变笨。

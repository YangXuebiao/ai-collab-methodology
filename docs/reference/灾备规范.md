# 灾备规范

> 适用场景：断电、崩溃、换电脑、对话丢失、状态文件损坏。目标：**零信息损失、项目不中断**。
> 前提：**项目状态都在磁盘上，不在对话里**。磁盘不丢 = 项目不丢；这条不成立，下面全部失效。

## 一、为什么灾备能做

AI 对话易失（关窗口、断电、换机器就没了），磁盘文件持久。

所以灾难的真正代价不是"丢了什么"，而是"**没了对话，人不知道该从哪接**"——灾备要让磁盘上的文件本身足以回答"现在什么状态、下一步做什么"。推论：**只存在于对话里的结论等于不存在**，做完一件事就落盘。

## 二、四层恢复（顺序不能换）

```
灾难
 ↓
第一层 磁盘自恢复    读状态文件 + git status，知道"现在在哪"
第二层 文件契约恢复  读设计文档 → 实现状态 → 验收报告，重建上下文
第三层 git 历史恢复  文件损坏 → 从历史版本恢复
第四层 人脑恢复      以上都失败 → 人描述当前状态
```

**前两层足够应对绝大多数灾难**，后两层是兜底。顺序不能换的原因：**先定位，再重建，最后才是修损坏**——反过来（一上来就翻 `git log`、就 `checkout`）是在不知道目标状态的情况下瞎试，越试越乱。

## 三、状态文件：这一步得你自己做

没有自动化的钩子，所以**你需要自己维护一个状态文件**（提交进仓库，跟代码一起走）。最小要求四个字段，会话开始和结束各改一次：

```json
{ "session_active": true, "phase": "developing",
  "last_active_role": "developer", "last_action_at": "2026-09-22T10:30:00" }
```

**崩溃检测靠的就是 `session_active`**：干净退出会把它置回 `false`，断电/崩溃不会——下次打开它还是 `true`，等于"上次没好好收尾"。

**代价要说清：自维护的标记必然有假阳性**，人就是会忘记收尾。所以先分两类：

| git status | 判定 | 处理 |
|---|---|---|
| 干净（无未提交改动） | 大概率只是忘了收尾 | 清除标记，正常开始 |
| 有未提交改动 | 确认是中断 | 走完整恢复（§四） |

**为什么必须分**：如果十次"崩溃"里有七次只是忘了收尾，人很快就不信这个信号了。**一个不再被信任的告警等于没有告警。**

## 四、场景与恢复步骤

**场景 1：断电 / 崩溃 / 关窗口（最常见）**

损失：对话上下文没了，磁盘完好。恢复：

1. 在同一个项目目录开一个新对话
2. 让 AI 读状态文件；若 `session_active: true`，输出恢复摘要（当前阶段 / 上次的活 / 上次操作时间）+ `git diff --stat` + 最近几条提交
3. **人确认**后再继续，收工时清除标记

**信息损失：零**。最多丢掉"AI 脑子里还没写下来的下一步计划"——所以实现状态文件里必须有"还剩什么"。

**场景 2：换电脑 / 迁移仓库**

`git clone` → 按技术栈文档装依赖 → 开新对话读状态文件 → 继续。旧机器还有未提交改动时，先 `git stash push -m "interrupted-work-$(date +%Y%m%d)"`。**注意 stash 不是分支，`git push` 推不走它**——要把这份改动带走，得先把它落成一个真分支：`git stash branch interrupted-work-$(date +%Y%m%d)`（该命令会切到 stash 的基线提交、把改动应用上去，成功后就地丢弃 stash），再 `git push -u origin interrupted-work-$(date +%Y%m%d)`。推不走（旧机器已经连不上）就按实现状态文件重建。

**场景 3：状态文件损坏或丢失 / 人忘了到哪一步**

看 `git log --oneline -10`（最近做了什么）、`git diff --stat`（磁盘上有什么没提交）、`ls docs/specs/`（有哪些版本），再用 §五 的对照表推断。

## 五、从磁盘重建状态（核心方法）

**对话没了不要紧，只要文件在。**按"磁盘上有什么"反推"现在该干什么"：

| 磁盘上有 | 处于什么状态 | 下一步 |
|---|---|---|
| 有设计文档，无实现状态 | 刚设计完，还没开工 | 派活实现 |
| 有实现状态但未完成 | 做到一半 | 继续实现（读"未完成/阻塞"节） |
| 实现完成，无验收报告 | 做完了，没验 | 开始验收 |
| 有验收报告 | 待审查 | 审阅、收尾 |
| 有完成报告 | 这一版结束 | 规划下一版 |

**单个文件丢了也能重建**：实现状态丢了 → 读设计文档（知道要做什么）+ `git diff`（知道做了什么）；验收报告丢了 → 读设计文档里的验收标准 + 重跑测试。三份文件互为备份，构成**三角验证**——丢一份不致命。

## 六、处置底线：不确定时先问人

恢复过程中最危险的动作是"我猜是接着这里做"，然后一路做下去。

**判据：如果你无法用一个磁盘文件证明"当前状态是什么"，就不要开工。**把推断摆出来（"磁盘上看到 A、B、C，我推断处于 D 阶段"），让人确认或纠正。**为什么**：代价不对称——问一句花 1 分钟；猜错是几十分钟的白干，而且是在你以为它在做别的事的时候发生的。

## 七、预防与不可恢复

| 预防措施 | 效果 |
|---|---|
| 每完成一个子任务就更新实现状态 | 磁盘上始终有最新进度 |
| 会话结束清掉 `session_active` | 崩溃信号才可信 |
| 未提交改动 `git stash` + 描述性 message | 中断的工作不丢 |
| 定期 `git push` | 远程备份，本机炸了还能活 |

**真的没救的情况**（别指望灾备，靠上面的预防）：

| 情况 | 为什么没救 | 缓解 |
|---|---|---|
| 磁盘物理损坏 + 无远程备份 | 数据读不出来 | 定期 push |
| `.git/` 损坏 | 版本历史全丢 | 异地/远程备份 |
| 所有状态文件同时损坏 | 上下文全丢 | 多文件互备（§五） |
| 只活在对话里的决定 | 从来没落过盘 | §一 推论一 |

## 八、部署层数据安全

> 从真实生产事故里泛化的经验：**默认配置就该扛得住误操作**。

| 原则 | 含义 |
|---|---|
| 假设最坏操作会发生 | 任何命令都可能被执行在错误的目标上。配置要扛得住 `docker compose down -v`、容器被误删 |
| 数据安全默认开启 | 持久数据不该因为一条命令就没了 |
| 显式优于隐式 | 绝不依赖上下文推断破坏性操作的目标；必须显式写"生产服务器"或"你本地机器"，禁止"当下系统"这类模糊说法 |
| 冗余不是可选项 | 关键资产（数据库、镜像）必须有副本。"幸亏本地还留着"不是策略 |

**持久数据用 bind mount，不用 named volume**：`./data/postgres:/var/lib/postgresql/data` 这种写法，`docker compose down -v` 不会删掉宿主机目录；named volume 则会被清掉——准确说，`down -v` 删的是 **compose 文件里声明**的命名卷与匿名卷；标了 `external: true` 的外部卷不在此列，但那份豁免挂在 compose 文件之外，是隐式的、翻文件才看得见，靠它不如靠 bind mount 直接。数据目录别硬编码，用环境变量（如 `DATA_DIR`）留出外部配置的口子。

**定时备份 + 保留策略**（最近 7 天每日 + 最近 4 周每周）：

```bash
# ⚠️ 复制前先把占位符换成实际值，别直接粘进终端 —— 未替换的 <db> 会被 shell 当重定向符解析，
#    报的是 "db: No such file or directory"，你看不出是自己没替换占位符。
#    crontab 不继承你登录 shell 里的变量，所以变量赋值要写在 crontab 文件里（下面这几行即是）。

DB_CONTAINER=app-db
DB_USER=app
DB_NAME=app_db
IMAGE=myapp
TAG=v1.2.0

# 每日 03:00 dump 到 bind mount 下的备份目录
0 3 * * * docker exec "$DB_CONTAINER" pg_dump -U "$DB_USER" "$DB_NAME" > /srv/app/data/backups/daily-$(date +\%Y\%m\%d).sql
docker save "$IMAGE:$TAG" -o /srv/app/backups/"$IMAGE"-"$TAG".tar   # 关键镜像留 tarball
```

**cron 里跑 `docker` 另有两个坑**：① crontab 的 `PATH` 通常只有 `/usr/bin:/bin`，`docker` 要是不在其中（常见于 Docker Desktop / 自装到 `/usr/local/bin`）就直接 `command not found`——先用 `command -v docker` 查出绝对路径，把上面命令里的 `docker` 换成它；② cron 不会加载你的登录会话，未必带 docker 组凭证，非 root 用户跑 `docker` 会 permission denied——要么把执行用户加进 `docker` 组，要么确认 `sudo` 在该 cron 下免密。这两条都建议**先手动跑一次同一条命令**（`env -i /bin/sh -c '...'` 可模拟 cron 的空环境）再放进定时任务。

**破坏性操作前，三段式确认**：① 显式声明目标（"即将在**生产服务器**上执行"）② 列出受影响资源（容器、卷、网络、镜像）③ 最后确认（"此操作不可自动撤销，确认？"）。

## 一句话总结

> **灾备不是"备份文件"，是"保证文件里写着足够重建状态的信息"。**

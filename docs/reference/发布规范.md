# 发布规范

> **适用场景**：你要把软件交出去——部署到服务器、发给用户、打包给同事。这一篇讲两件事：**什么条件下才算可以发布**，以及**发布产物该长什么样**。
> 一个人开发也适用；怎么按自己的规模裁剪，见第七节。

## 一、前提：发布是有门槛的

**"打包 + 上传"不是发布。**健康检查通过 ≠ 业务可用；进程活着 ≠ 功能能跑。发布是**有门槛的动作**——条件不满足就不发，而不是"先发了再说"。门槛由两半组成：**人能拍板的**（发哪个版本）与**机器能判定的**（检查项全绿），缺一不可、也不能互相替代。还有一条：发布不该有"现场发挥"的空间，每次走同一条固定流程。

## 二、版本号是对外承诺的锚点

**这是本篇最重要的一条认知。**版本号不是程序可以随意递增的计数器——它回答的是「**哪个版本是已验证、可发布的**」。程序若能擅自 bump，版本号就失去了这个含义，用户也无从知道你给他的到底是哪一版。

### 2.1 人类定上限，程序不越界

版本号由**人（项目 owner）** 定上限（ceiling），程序只能在 ceiling 以下的预留槽位内协调迭代。ceiling 升级必须先经人确认。

| 槽位 | 用途 | 谁定 |
|---|---|:---:|
| **ceiling（最新正式版）** | 默认发布版本 | 人类 |
| ceiling−1 | 迭代 / 协调 | 程序 |
| ceiling−2 | 快照 / 回退 / 实验 | 程序 |
| ceiling−3 | 上一个正式版存档 | 自动 |

四条铁律：**程序不越 ceiling**；**默认用 ceiling**（覆盖，不自动递增）；**预留 2 槽位**供程序协调，不新增版本号；**归档槽位**存上一个正式版。

### 2.2 bump 必须由人确认

**AI 在未获明确授权前，不得自行 bump 版本号。**需要调整时先说清「从 X 改到 Y + 改动范围 + 依据（breaking / feature / fix）」，人确认后再动手。**为什么**：对外版本号是给用户的承诺，承诺不能由程序单方面改写。

**建议加固**：若你的 AI 工具支持命令拦截钩子，把「未带版本确认就执行发布」做成硬拦截；做不到就用流程纪律兜底——但要清楚这一层是软的。

### 2.3 版本号散落多处，bump 要一次性同步

版本号常硬编码在多处：构建脚本、发布清单、产物文件名、依赖清单、变更日志，甚至测试断言。**改一处漏一处，就会出现「清单说 v0.3.0、产物却叫 v0.2.0」这种自相矛盾。**落地：先 `grep -rn "<旧版本号>" .` 看全貌 → 逐处改 → 再 grep 一次确认零残留。

## 三、发布门槛：可判定的验收条件

### 3.1 冒烟必须覆盖核心业务

**只验 `/health` 不算冒烟。**它只证明"进程活着"——一个依赖没装好、一个模型没加载，health 仍可能返回 200。**判据**：跑一条端到端的**核心业务请求**（一次真实查询 / 计算 / 下单），失败即阻断发布。

### 3.2 派生数据必须显式重建

可重算的派生数据（模型、缓存、聚合表）**必须在部署流程里显式重建一步**，不能假设它已存在，否则会出现"正式库表空 → 功能空转"。**落地**：部署流程加"重算 / 训练"步骤，**再加一道定时任务兜底**。

> 定时任务若与其他服务共用，**禁止整表替换**：只做增量合并，只按你自己带标记的行过滤，安装前后自检「别人的任务条数未减少」。历史上就因按日志文件名做模糊过滤，误删了同机另一服务的备份任务。

### 3.3 发布文档与版本同步

README / 变更日志 / 发布清单必须与当前版本一致。**文档不完善 = 不能发布。**发布前逐项核对：迁移号、健康检查响应、功能清单、定时任务、产物大小、构建信息。

### 3.4 门禁：把可判定的检查交给机器

上面几条只写进文档等于没有——**赶进度时没人会逐条自查**。你需要一个**门禁脚本**（名字随你，关键是有"一个等效的唯一入口"）：一条命令跑完全部可判定检查，任一项失败即中止，并打印"哪项、差在哪"。

| 类别 | 检查项 | 判据 |
|---|---|---|
| 源码 | 版本号唯一 | 所有硬编码版本号取同一值 |
| 源码 | 测试 / 类型 / 依赖 | 测试 exit 0、静态检查 0 error、漏洞扫描 0 高危 |
| 源码 | 迁移完整 | 无 pending 迁移，schema 与迁移脚本一致 |
| 产物 | 产物自完备 | 必需文件全在 + 禁止文件全无 |
| 产物 | 产物最新 | 产物版本号 == 源码版本号，且**内容含当前 commit**（防"文件在、内容是旧的"） |
| 产物 | 文档与安全 | README + INSTALL 存在且含必需章节；不含真实密钥 / 密码 |

> ⚠️ **「加了检查」不等于「检查有效」。**永远绿灯的检查比没有检查更糟——它给虚假的安全感。落地一条检查后**故意违反一次，确认它真的变红**（历史事故：某检查器因目标目录不存在，三项检查全空转后打印 ✅）。
> ⚠️ **反面同样有害：常红的门禁等于没有门禁。**只在特定条件下适用的检查（如"本版本改了指标就必须附结构完整的评估报告"），**不适用时要显式 skip 并放行**；同理，依赖外部漏洞库的联网检查遇到网络超时也该 skip，而不是误报成"有漏洞"。否则噪音会让人养成绕过门禁的习惯。
> 📌 **诚实边界**：脚本**要你自己写**，本篇不给现成实现。上表是"该覆盖哪些类别"，具体文件与命令只能你自己填。也别指望 CI 代劳——CI 能跑门禁，门禁内容仍是你写的。另：编译 / 打包型产物可能**剥离未使用的常量字符串**，直接查二进制会查不到，改为构建时把 commit 写进一个**确定会打进包的资源文件**，门禁解包后校验。

## 四、单一自包含发布产物

> **精神**：对外发布只有一个权威出口——一个自包含、恒新、面向 0 基础受众的产物目录（下称 `dist/`）。

- **唯一出口**：产物不散落各处，只有它是"给外界的"；**生成方式唯一**（一条命令从源产出，禁止手动拼装）
- **源码 / 测试 / 内部文档草案不进产物**；**每次发布重新生成**，不留旧版本（或显式归档）
- **禁止出现**：真实 `.env`（密钥）、运行时数据目录、缓存与构建垃圾

```
dist/
├── <可运行产物>      # 镜像 tar.gz / 二进制 / 安装包
├── <部署配置>        # compose 文件 / 配置文件
├── <环境变量模板>    # .env.example，含所有需填项 + 注释
├── <部署脚本>        # 一条命令部署，内置加载产物、初始化配置
├── <回滚脚本>        # 一条命令回滚
├── <发布清单>        # 版本 / 日期 / commit / 产物名，含历史（回滚要用）
├── README.md         # WHY：这是什么、为什么这样设计
└── INSTALL.md        # HOW：逐步怎么装、怎么验证、怎么回滚
```

**「0 基础可部署」怎么验收**——不是 grep 文档里有没有某个标记，而是**真跑一遍**：把 `dist/` 复制到全新环境，只按 `INSTALL.md` 复制粘贴，服务起来，冒烟通过。干净环境 = 不依赖现有服务器、不依赖已有数据 / 密钥、不依赖旧系统网络。**落地动作**：发布前自己假装 0 基础，**卡住的地方就是文档要补的地方**。

**文档两层，缺一不可**：README 答 WHY（这是什么、为什么这样设计），INSTALL 答 HOW（逐步怎么装、怎么验证装好了、怎么回滚）。**判据**：读 README 能回答"为什么"，读 INSTALL 能照着做"怎么做"。只有命令清单没原理 → 补 README；只有原理没可复制步骤 → 补 INSTALL。

> **注意**：「0 基础可搭建」是方向，不是绝对门槛。静态站能做到复制粘贴部署，复杂分布式系统做不到——门槛随复杂度浮动，但方向永远是"尽可能接近复制粘贴可部署"。

## 五、部署入口的六项契约

你的部署脚本（名字随你，自己实现一个等效入口即可）必须明确以下六项，缺一项即不合格——**目的是消除"每次现场发挥"**：

| 契约项 | 要求 |
|---|---|
| 入参语义 | 每个 flag 明确（"仅构建" / "仅部署" / "确认版本号" / 无参=全流程） |
| 退出码 | 0=成功；非 0 **区分**"门禁不过 / 构建失败 / 传输失败 / 部署失败 / 冒烟失败" |
| 幂等性 | 重复跑安全（定时任务增量合并、迁移幂等） |
| 失败语义 | 说清每步"失败=阻断"还是"失败=告警"（门禁、构建、部署必须阻断；非核心冒烟可告警） |
| 日志 | 分阶段打印，关键结果（版本、产物大小、冒烟结果）显式输出 |
| **版本确认** | 发布（非仅构建）前**必须人工确认版本号**，防 AI 擅自发布错误版本 |

**内置门禁**：部署脚本第一步就跑发布门禁，不过不进构建。**没有"跳门禁直发"的后门。**

## 六、回滚与审计：任何规模都必须有

**发布不是"只能往前"，必须"能退回来"。**这两项是红线——**个人项目同样会出生产事故**，那时没有回滚，损失是全额的。**回滚需要三样**：旧产物还在（或发布清单记着历史版本标识）、数据有快照（部署前 dump）、一条命令能退回（如 `rollback.sh <version>`）。

> ⚠️ **恢复顺序是踩过坑的铁律：先恢复数据，再启动应用。**反过来会出现"应用启动时的迁移逻辑先建了表" → "恢复快照时建表语句撞上已存在的表" → **回滚失败**。顺序错了，安全网就是破的。

**一个来自实践的简化**：「能精确回到任意历史版本」在运维上是**过度设计**——快照堆多了，没人知道哪个是稳定版。更实用的是**通常只保留两个有意义的标签**：`<版本>`（当前运行）与 `<版本>-pre`（稳定版存档）。这**两个标签在同一次发布里一动一改，次序是先追加、后删旧**：先把即将被替换掉的版本打上 `-pre` 存档（追加），再删掉上一个 `-pre`（删旧）——反过来会有一段"没有可回退版本"的空窗。版本号编码在标签名里，回滚时从标签名读，**不靠审计日志、不靠 commit hash、不靠人记**。

- **回滚后标签必须复位**：把存档标签改回版本标签，**不留 `-pre`**，否则下次发布的存档链就断了。
- **备份要自动清理**：部署前快照、产物归档会无限累积，**保留最近 N 个，其余自动清掉**，否则磁盘会被历史快照吃满。**N 不是虚指，要自己定死一个数**（常见取 5～7 个，够覆盖"上一版出事、上上一版才稳"的情形）。**并且 N 就是你的回滚深度上限**：没有制品仓库时，旧产物只存在这台机器上，被清掉的第 N+1 个版本就再也回不去了——要回退更远，只能靠制品仓库（§七 进阶层）或发布清单里记着的历史版本标识。

**审计**：每次发布**自动追加**一条记录（机器写，不靠人肉），至少含 版本 / 时间 / commit / 谁发的 / 发布了哪些端 / 门禁结果 / 冒烟结果 / 可回滚到哪。落进仓库、进 git——**出问题时你唯一能问的就是这几个字段**。

## 七、分层与裁剪：按你的规模选，不要照单全收

> **这一段是给你减负的。**上面每条都成立，但**不必一次全上**。

| 分层 | 适用 | 必做 |
|---|---|---|
| **基础（任何项目）** | 单实例、个人 / 小团队 | 版本受控 + 门禁 + 自包含产物 + 一键部署 + 冒烟 + **回滚** + **审计** |
| **进阶（应该做）** | 多实例、团队协作、持续交付 | 基础 + CI/CD（打 tag 自动发布）+ 制品仓库 + 多环境（dev/staging/prod） |
| **大规模** | 高可用、灰度 | 进阶 + 金丝雀 / 蓝绿 / 滚动发布 + 灰度开关 + 发布后监控告警 + 灾备演练 |

裁剪的规则是**"晚点补"，不是"不用有"**：先上基础层，规模变大时**只增不减**，不推翻重来。**但基础层里的"回滚 + 审计"没有裁剪空间**——它是下限，不是上限。

## 八、两条从事故里换来的脚本铁律

**教训**：一次发布连挂三次，日志里**没有任何报错**。原因是 `set -e` 下，`[ -d x ] && mv` 作为函数**末语句**时，目标缺失会短路返回 1，函数返回非零 → 调用处静默退出（**前提：调用语句自身不在 `if` / `&&` / `||` / `!` 这类被测试的上下文里**，否则不会退出——所以「同一个函数会不会炸掉整个脚本」取决于调用点，不是函数本身）。靠 `bash -x` 才定位。

所有构建 / 部署脚本必须配置 `trap ERR`，退出时打印失败行号 + 命令。**注意 `-E` 不能省**——ERR trap **默认不继承进 shell 函数**，而脚本逻辑几乎必然封装在函数里；少了它，失败发生在函数内时拿到的是**调用行**和**函数名**，而不是真正的失败位置。bash 自己的说明就是证据：

```
$ bash --help | grep -A0 '\-E'
      -E  If set, the ERR trap is inherited by shell functions.
```

```bash
set -Eeuo pipefail   # -E：ERR trap 才能继承进函数
trap 'echo "[ERROR] ${BASH_SOURCE[0]}:${LINENO} 函数:${FUNCNAME[0]:-main} 命令失败: ${BASH_COMMAND}"' ERR
```

另外：**`[ -d x ] && cmd` 别当函数末语句**——默认改成 `if [ -d ]; then ...; fi`（条件为假时 if 整体返回 0，不留非零尾巴）；**`|| true` 只在「我确认这里失败可以忽略」时才用**，因为它会连带吞掉 `cmd` 自身的失败，与上面那条 ERR trap 的用意正好相反；**构建前做环境预检**（依赖、目标主机可达），让它在第 1 秒就失败而不是构建到一半才炸；**静默失败第一时间 `bash -x` 追**，别靠重复重跑猜。

> **信息唯一性**：发布怎么做只应有一个权威来源（本篇 + 你的门禁脚本 + 部署脚本 + 产物内的 README/INSTALL）。其他文档**只引用、不复述**——多处复述就是信息不唯一的信号。

# 评估规范

> **适用场景**：算法选型、模型迭代、检索调优、性能优化、数据清洗——
> **任何"用一个数字判断好坏"的场合。**
>
> 与技术栈无关：回归、检索、推理、渲染、构建，一律适用。
> 这是 [06-质量与验收.md](../06-质量与验收.md) §四的**操作展开版**——那篇讲原理，这篇给你可抄的模板。

---

## 一、为什么需要它（一次真实事故）

一次算法选型，AI 用**「10 个参数的平均误差」**对比三个方案，得出结论：

> 「方案 C 最优，优于其他 17~33%」

并且**多轮"验证"都维持这个结论**。

后来换用**尾部指标（P90）**重新评估，发现：

> **方案 C 在某个参数上，尾部误差比其他方案差 20~100 倍。**

它只在中位数上略好，**尾部灾难性地差**。结论被彻底推翻——方案 C 其实是最差选择。

### 根因：尺子错了，不是算错了

- 各参数**单位天差地别**（一个 ~1.6，一个 ~67），跨参数求平均**在数学上就没有意义**
- 这个平均恰好**掩盖**了单项的 20~100 倍回退
- 此后每一轮"验证"都用**同一把看不见问题的尺子**，自然每轮都得到同一个"好"结论

> **多验证几轮纠不了这种错。换指标比多验证更重要。**

## 二、六条铁律

### 铁律 1：先定"真正关心的指标"

用反映**业务/用户关切**的指标，不用"方便统计"的指标。

**判据**：报告须显式写出「本次评估的口径」，并说明它对应哪个关切维度（精度？极端情况？成本？风险？）。**写不出对应关系 = 未通过。**

### 铁律 2：禁止用聚合指标下结论

**禁止只凭聚合指标下结论。**聚合数本身没有问题——整体准确率、平均延迟、总吞吐都是合法指标。出问题的是**用它下结论而不给逐项明细**：平均值会把某个子集的灾难性回退平均掉。任何"整体 XX%"都必须**同时**给出逐项对比表。

**判据**：报告须含**逐项对比表**（每个被评估对象一行）。只给聚合数 = 未通过。

### 铁律 3：尾部指标并列

必须**同时**给出 `p50 / p90 / p99 / max`（或该领域的等价口径），**不得只给中位数或均值**。

**判据**：逐项对比表须含至少一个**尾部列**。缺 = 未通过。

> **用户实际遇到的往往是尾部情况**，而中位数看不见尾部灾难。

> ⚠️ **样本量前提（别忽略）**：分位数需要样本支撑。**n < 100 时 `p99` 不可估**——nearest-rank 口径下它就等于 max，并列两列是虚假的精度。样本不足时改为只报 `p50 / p90 / max` 并注明样本量。
> 另外 **`max` 是单次观测**，方差最大，一次抖动就换一个值。它适合当「有没有发生过灾难」的哨兵，**不适合拿去比较两个方案的比值**。

### 铁律 4：先做「旧 vs 新」逐项对比，标出**所有**回退

对比表须**同时含旧值与新值**，并**逐项标出**哪些变差了。

**判据**：列须含「旧值 / 新值 / 变化」三列；回退项须显式标记。缺 = 未通过。

### 铁律 5：回退超阈值即停

**阈值必须在评估前声明**，不得看完结果再定。任一子集回退超阈值 → **停下来查，不得放行**。

**判据**：报告须含「阈值声明」节。**事后补的阈值 = 未通过。**

> 看到结果再定阈值，阈值就沦为**事后合理化**——总能定一个刚好能通过的数。

> ⚠️ **两个补丁**：
> **① 无法前置时怎么办**（新指标、没有历史基线）：不要就此判「未通过」——那会把「先探索、再在留出集上确认」这条正路也堵死。做法是**在一批新数据上验证该阈值**，并明确标注「此阈值来自探索阶段，不得作为本次放行依据」。
> **② 子集多时要防噪声**：子集一多，纯噪声也会让个别子集越线（每个子集 5% 概率的话，50 个子集下期望 2.5 个越线）。只对**预先指定的关键子集**设硬阈值，其余用多重比较校正后的口径。否则「停下来查」会变成常态噪音——**常红的门禁等于没有门禁**（见 [发布规范](发布规范.md) §3.4 同一条道理）。

### 铁律 6：结论必须附「反例 / 还没查什么」

**禁止只列支持证据。**每下一个结论，须同时给出：有没有反例？哪个子集会变差？我还没查什么？

**判据**：报告须含「反例 / 未查项」节且**非空**。只有支持证据 = 未通过。

## 三、报告模板（复制即用）

```markdown
## 评估口径
- 关切维度：{精度 / 极端情况 / 成本 / 风险}
- 指标：{为什么这个指标反映上面的维度}
- 尾部口径：p50 / p90 / p99 / max
- 回退阈值：{数值}（依据：{…}；评估前声明）

## 逐项对比（旧 vs 新）
| 对象 | 旧 p50 | 新 p50 | 旧 p90 | 新 p90 | 旧 p99 | 新 p99 | 旧 max | 新 max | 回退? |
|---|---|---|---|---|---|---|---|---|---|
| {obj-1} | | | | | | | | | ⚠️/— |

## 回退清单
- ⚠️ {obj}: {指标} 从 {旧} → {新}（{倍数}），{是否超阈值}

## 反例 / 还没查什么
- 反例：{…}
- 未查：{…}

## 结论
{结论} —— 依据上面的逐项表。
若无反例与回退，明写「未发现反例，未查项为 {}」。
```

## 四、反例对照

| ❌ 错误做法 | 后果 | ✅ 正确做法 |
|---|---|---|
| 跨单位求平均 | **无意义**，且掩盖单项 20~100 倍回退（**已致事故**） | 改用逐项对比表；或**先归一化**（相对误差 / 变化率）再聚合 |
| 只报中位数 | 看不见尾部灾难；用户遇到的恰是尾部 | `p50 / p90 / p99 / max` 四项并列 |
| 只给新值，不给旧值 | 无法判断谁变差了 | 旧值 / 新值 / 变化 三列 |
| 看到结果再定阈值 | 阈值沦为事后合理化 | 阈值**评估前**声明 |
| 只列支持结论的数据 | 越验证越像凑支持，纠不了错 | 附**非空**的「反例 / 未查项」节 |
| 出问题先归因数据 / 环境 / 历史 | 漏掉"是不是我刚改的导致的" | **先查自己的改动，再查外部** |

## 五、在你的项目里怎么落地

不用一次全上。

1. **先盘点现状**：你现在的评估用什么指标下结论？有没有跨单位求平均的地方？把它们列出来。
2. **只覆盖关键路径**：先给"会影响用户/业务结果"的那条路径加对比表（算法、检索、推荐），不是所有地方一起改。
3. **阈值从宽到严**：首次引入时阈值可以宽（先养成逐项看的习惯），但**必须前置声明**；成熟后再收紧。
4. **允许"不适用"**：纯展示层、无指标输出的模块不必强行引入——但要**显式记录下来**「此处不适用」，不记就等于遗漏。

## 六、边界：「用户直觉」与「成事不讨好」

这两条看起来冲突，实际不冲突：

> **用户的直觉当「触发信号」（换个指标重测），不当「结论」（直接照做）。**

- ✅ 用户说"太绝对了" → **立刻换指标（尤其尾部）重测** → 用数据说话
- ✅ 重测后数据支持原结论 → 如实说"换指标重测后仍成立"，给出证据
- ⚠️ **事后换指标必须披露**：报告要**同时列出旧口径与新口径两组数字**，并显式声明「本次指标为事后切换」。看完结果再挑指标，与铁律 5 所禁的「事后定阈值」是同一族错误（选择效应）——**换对了，不代表流程对**
- ❌ 用户说"太绝对了" → 不测就改口（**这是讨好**）
- ❌ 用户说"太绝对了" → 不测就继续辩解、堆更多同口径的数据（**这是这条规范要治的病**）

**注意**：那次事故里，正是用户"凭直觉觉得太绝对了、像在凑数据"的质疑，才发现了问题。**直觉是宝贵信号，只是它需要被转化成验证动作。**

---

## 七、诚实的边界

这套规范**大部分不可机器检查**。

"这条指标是否反映了真正的关切"是**判断**，不是模式匹配。你能自动检查的只有**报告结构**（有没有逐项表、有没有尾部列、反例节是否为空）——而这需要你自己写脚本。

**不要因为"报告格式对了"就认为"评估是对的"。**格式对只是必要条件。

# 文件契约：AI 之间怎么传递信息

> **一句话**：不靠人在对话之间转述，靠磁盘上的结构化文件。
>
> 下一个 AI 读到的，是上一个 AI **自己写的**，不是你翻译过的。

---

## 为什么不用"直接说"

你可能觉得：反正都是我在跟 AI 聊，我把上一个对话的结论贴给下一个不就完了？

问题在于**每转述一次就失真一次**：

- 你会漏掉细节（不是故意的，是人的记忆本来就会压缩）
- 你会加入自己的理解（"它的意思应该是……"）
- 你会丢掉不确定性（AI 说"这里我假设了 X，如果不是请纠正"——转述时这句最容易丢）

用文件：**原文传递，零失真**。

还有个更实际的好处：**文件是持久化的**。对话会滚走，文件不会。三天后你回来看，还在。

---

## 六个文件

| 文件 | 谁写 | 谁读 | 解决什么问题 |
|---|---|---|---|
| **spec**（设计文档） | 设计者 | 实现者、验收者 | 这一版要做什么、怎么算做完 |
| **task-card**（任务卡） | 设计者 | 实现者 | 具体做什么（可执行粒度） |
| **dev-status**（实现状态） | 实现者 | 设计者、验收者 | 做到哪了、卡在哪、有什么假设 |
| **qa-report**（验收报告） | 验收者 | 设计者 | 验证结果、发现的问题 |
| **handoff**（交接） | 任何人 | 下一个对话 | 上下文快满时把状态交出去 |
| **completion-report**（完成报告） | 设计者 | 未来的你 | 这一版最终交付了什么 |

**注意"谁读"那列**——每个文件都有明确的读者。写文件时想着读者，格式自然就对了。

## 一、spec（设计文档）

**最重要的一份。**它定义了"这一版要做什么"和"怎么算做完了"。

### 关键部分

```markdown
# V{x.y.z} {功能名} — 设计 Spec

## 一、背景与目标
   为什么要做这一版？当前有什么问题？做完之后什么样？

## 二、依赖选型
   新增/变更了哪些依赖？为什么选它？（注意：这属于 B 类决策，见 05）

## 三、目录结构
   新增/改动的文件放在哪

## 四、核心设计
   具体怎么做。分模块写。

## 五、与已有代码的接口
   会影响到谁？改了哪些既有接口？

## 六、测试策略
   怎么测？测到什么程度？

## 六b、评估口径与基线   ← 涉及指标/性能/算法改动时必填
   见 06-质量与验收.md。这一节最容易漏，但漏了代价最大。

## 七、文件清单
   逐文件列出：新增/修改/删除

## 八、验收标准              ← 没有这一节，spec 就是废纸
   逐项写出可判定的验收条件
```

### 「七、文件清单」和「八、验收标准」为什么单独强调

**文件清单**让实现者知道边界在哪——不改清单外的文件。

**验收标准**是整份 spec 里**唯一必须可判定**的部分：

```markdown
❌ 不合格：登录功能正常工作
✅ 合格：  错误密码连续 5 次后，账号锁定 15 分钟；
          第 6 次尝试返回 429 且提示剩余锁定时间
```

**判断方法**：写完之后问自己——**"这条标准能不能被一个没参与设计的人，看着它就能判断通过还是不通过？"** 不能，就是没写好。

### 修订记录

spec 改了就记一笔：改了什么、为什么。**不要静默修改 spec**——下游可能已经按旧版做了。

---

## 二、task-card（任务卡）

spec 是设计文档，任务卡是**可执行的分派**。一份 spec 可能拆成多张任务卡。

### 关键部分

```markdown
## {标签} 任务卡 — {一句话描述}

### 你只需要知道这些（5 行以内）
   ← 不要求实现者读完整份 spec

### 要做什么（逐一对照，每项一行）
   ← 原子项清单，≤12 项（见原则 8）

### 关键约束（只写这次涉及的，不贴整份规范）

### 不要碰（文件级清单——列出具体文件名）
   ← 不是笼统说"别碰别的"

### 完成后做什么
   ← 更新哪个文件、怎么报告

### 角色边界提醒
```

### 三个设计要点

**「你只需要知道这些」**：任务卡的价值在于**让实现者不用读完整的 spec**。如果一张任务卡要求对方先读 2000 字背景，那它就失败了。

**「不要碰」必须是文件级**：
```
❌ 不要改其他地方
✅ 不要碰：src/config/settings.py、tests/test_auth.py
```
笼统的"别乱改"没有约束力。具体文件名有。

**原子项 ≤12**：超过就拆成两张任务卡（见原则 8）。

## 三、dev-status（实现状态）

实现者写，**记录"做到哪了"和"我做了什么假设"**。

```markdown
# V{x.y.z} 实现状态

## 已完成
- [x] 原子项 1（文件:行号）
- [x] 原子项 2

## 未完成 / 阻塞
- [ ] 原子项 5 —— 卡在：<具体原因>

## 我做的假设      ← 最重要的一节
- 假设 <X> 是 <Y>，如果不是请纠正

## 偏离 spec 的地方
- 无 / <具体偏离 + 理由>

## 磁盘上的改动
- 修改：<文件清单>
- 未提交（等设计者审查）
```

### 「我做的假设」为什么单列

实现过程中一定会遇到 spec 没写清楚的地方。实现者会自己填一个，然后继续。

**这个填充如果不写下来，就永久丢失了**——将来出问题时，没人知道当初这里是"猜"的。

---

## 四、qa-report（验收报告）

```markdown
# V{x.y.z} 验收报告

## 逐项验收（对照 spec 第八节）
| 验收标准 | 结果 | 证据 |
|---|:---:|---|
| 连续 5 次错误密码后锁定 | ✅ | 见测试 test_lockout.py:45 输出 |
| 第 6 次返回 429 | ✅ | 见 curl 输出 |

## 发现的问题
| 级别 | 问题 | 位置 | 处理 |
|:---:|---|---|---|
| 🟢 | 类型标注遗漏 | auth.py:12 | 已修 |
| 🟡 | 缺失边界条件测试 | — | 记录，未改 |
| 🔴 | API 路径与 spec 不一致 | routes.py:30 | 记录，未改 |

## 未验证的部分      ← 必须写，不能空
- <哪些验收标准没验、为什么>

## 真实数据验证
- 用了什么真实数据 / 为什么没用
```

### 两个反直觉的要求

**「证据」列必须非空**：验收的每条结论都要能指向一个具体输出（测试结果、命令输出、日志）。**"我检查过了"不是证据。**

**「未验证的部分」不能空**：如果你全验完了，写"无"。但大多数时候是有遗漏的——**写出来，比假装全覆盖强得多**。

### 验收者自修的那几笔，由谁提交？

**由设计者在审查时连同实现者的改动一起提交。** 验收者的角色边界禁止它自己提交（见 [02-角色分工.md](02-角色分工.md)），所以设计者审 `qa-report` 时要**顺带看一眼验收者改的那几行 `git diff`**——发现改得不当时，应升格为 🟡 退回实现者。

> 不写清这一条，验收者的 🟢 修复会长期躺在工作树里无人提交；或者它为了"已修"生效而自行提交，直接违反角色边界。

## 五、handoff（交接）

上下文快满时写的文件，用来把工作搬到新对话。见 [04-上下文管理.md](04-上下文管理.md)。

结构见 [templates/handoff.md](../templates/handoff.md)。模板共八节，其中**「关键上下文（不看会踩坑的）」是它自己标注的"最重要的一节"**——没有它，接手的人会重走你走过的弯路。

**最简版至少要有四段**：当前状态 / 已完成 / 未完成 / 下一步（顺序执行）。

---

## 六、completion-report（完成报告）

一版做完后的收尾文档。最有价值的两节：

- **「已知问题」**：这版交付了什么、**留下了什么坑**。不写这一节，下一个版本会重新踩一遍。
- **「下一版本」**：这一版没做的事（以及为什么）。

---

## 让文件契约真正生效的三个条件

### 1. 格式固定

每次格式不一样，下一个 AI 每次都要重新理解——**就退化成了口头转述**。

**做法**：把模板放在 `templates/` 目录，让 AI 每次都从模板抄。

### 2. 单一负责人

一个文件只能有一个角色写。`qa-report` 由实现者写？那它就失去了独立性，整份文件的可信度归零。

### 3. 写的人要对读者负责

**每个文件都有明确的读者**（看开头那张表）。写的时候问：**读者拿到这份文件，能不能不问你任何问题就继续工作？**

不能，就是没写够。

---

## 单人开发怎么用

**可能有用的简化**：

| 完整版 | 单人简化版 |
|---|---|
| spec + task-card 分开 | 合并成一份「本版计划」 |
| dev-status 单文件 | 就在 spec 下面加一节「进度」 |
| qa-report 独立 | 保留（**这份别省**——它是独立验收的载体） |
| completion-report | 保留（**这份别省**——它是给未来的你写的） |

**最不该省的两份**：`qa-report` 和 `completion-report`。

前者是"客观验收"这件事的载体，省了就等于没有验收。后者是给三个月后的你看的——那时候你已经忘了当时的取舍理由。

# Spec（设计文档）模板

> **用法**：复制到 `docs/specs/V{x.y.z}-{名字}.md`，按需删减章节。
> 不适用的章节写「不适用」并给一句理由 —— **不要直接删掉**，删掉后读者分不清"没考虑"和"考虑过了不用"。

---

```markdown
# V{x.y.z} {功能名} — 设计 Spec

> 日期：YYYY-MM-DD · 状态：{草稿 / 待确认 / 已确认 / 实现中}

## 一、背景与目标

**为什么做这一版？**
{当前有什么问题 / 谁在受这个问题的困扰 / 不做的代价是什么}

**做完之后什么样？**
{一句话描述最终状态}

**不做的事**（明确的边界）：
- {这次不解决的问题} —— 因为 {理由}

## 二、依赖选型

{新增或变更的依赖，以及为什么选它}

> ⚠️ 引入**新的外部依赖/服务**属于 B 类决策，需先确认（见 [05-决策边界.md](../docs/05-决策边界.md)）
> 无变更写「无」

## 三、目录结构

{新增/改动的文件放在哪，体现什么组织思路}

## 四、核心设计

### 4.1 {模块 A}
{具体怎么做}

### 4.2 {模块 B}
{具体怎么做}

## 五、与已有代码的接口

{会影响到谁？改了哪些既有接口？调用方要怎么适配？}
无影响写「无」

## 六、测试策略

{怎么测？测到什么程度？哪些不测？}
{有没有需要真实数据才能测的部分？}

## 六b、评估口径与基线

> **凡涉及指标/算法/性能/检索质量改动，必填。** 其余情况写「不适用」。

- **关切维度**：{精度 / 极端情况 / 成本 / 风险}
- **指标**：{为什么这个指标反映上面的维度}
- **尾部口径**：p50 / p90 / p99 / max
- **回退阈值**：{数值}（依据：{…}；**评估前**声明，不得事后补）

详见 [06-质量与验收.md](../docs/06-质量与验收.md) §四（六条铁律）

## 七、文件清单

| 操作 | 文件 |
|---|---|
| 新增 | `path/to/new.py` |
| 修改 | `path/to/existing.py`（{改哪部分}） |
| 删除 | `path/to/old.py` |

**不在清单内的文件不改。**

## 八、验收标准          ← 最重要的一节

逐项写出**可判定**的验收条件：

1. {条件} —— 判定方法：{怎么验}
2. {条件} —— 判定方法：{怎么验}

> **判断标准**：一个没参与设计的人，看着这条能不能判断"通过还是不通过"？
> 不能 → 重写。

## 九、视觉方向（涉及 UI 时填）

{风格参考 / 色彩 / 布局要点}

## 十、交互行为清单（涉及 UI 时填）

| 元素 | 行为 |
|---|---|
| {按钮} | {点击后发生什么} |

## 十一、修订记录

| 日期 | 改了什么 | 为什么 |
|---|---|---|
| YYYY-MM-DD | 初版 | — |

> **不要静默修改 spec** —— 下游可能已经按旧版做了。
```

## 关于「待决策」的处理

设计过程中遇到 B 类决策（见 [05-决策边界.md](../docs/05-决策边界.md)）时：

1. **停下来** —— 不推进该分支
2. **记单子** —— 用 [decision-request.md](decision-request.md)，附在本文件后或单独存放
3. **绕开** —— 把不依赖这个决策的部分继续写完
4. **报告** —— 在交接时单列

**不要**在 spec 里写「TODO: 待定」就继续往下做。**那等于把决策的责任悄悄转移给了实现者。**
